# CK3 Version Analyzer

此 skill 的唯一维护入口在本目录；目录名保留 ck3_version_analyzer 以兼容现有项目。
仓库根 ck3_analyzer.py 是唯一分析实现，两处 skill 目录的同名脚本仅转发到它。
这是仓库内的 skill；单独复制目录时必须同时带上根脚本并调整转发路径。
运行环境为 Python 3.10+，脚本只使用标准库。

## 输入和任务范围

- 版本 A 是旧版本，版本 B 是新版本。尊重用户给定的顺序，不按文件夹排序猜测新旧。
- 可从当前目录列出 Crusader Kings III_* 和 CK3_* 目录，供确定输入；没有明确配对时先核实。短版本号仅精确匹配，存在多个匹配时要求完整路径。
- 默认交付最终解读报告和 B 站独立版。只有用户明确只要扫描或初步统计时，才在脚本阶段结束。
- 已有本次同一输入的 schema-v2 证据可复用；先核对绝对路径、版本提交、扫描口径和覆盖范围。目录内容变动、旧 schema 或来源不明时重新扫描。

## 执行扫描与证据提取

从仓库根目录运行以下实际命令；含空格的路径必须加引号。Windows 上 python 不可用时用 py -3。

~~~powershell
py -3 ck3_analyzer.py analyze "Crusader Kings III_1.19.0.4" "Crusader Kings III_1.19.0.5" --output-dir "diff_output_1.19.0.4_vs_1.19.0.5"
~~~

也可运行本目录的 ck3_analyzer.py，或为输入传入绝对路径。
相对输入路径基于当前工作目录；--base-dir 可指定另一基准。输出路径始终基于当前工作目录，且不得位于任一输入目录内。
保留旧的默认配对 1.18.4 → 1.19.0，但用户没有选择这组版本时，不应据此启动分析。

- --output-dir：默认按版本配对创建 diff_output_<旧版本>_vs_<新版本>。复用目录前确认不会覆盖仍需保留的证据。
- --max-deep-files：默认 0 表示全量文本分析；非零时先按审查优先级排序再限制，并记录跳过原因。
- --snippet-lines：每文件展示的原始差异行预算，默认 20；0 表示不限，正数至少为 2。
- --no-deep-analysis：只扫描和统计；修改文件的实际增删行数未计算，不得写成零。
- --encoding：无 BOM 文本默认严格 UTF-8；UTF-8/16/32 BOM 自动识别。已知其他编码可显式传入，不猜测或丢弃非法字节。
- --model：仅写入模型标签，不调用或切换模型。默认标明未执行 LLM 解读，完成解读后记录实际模型。
- --author：仅兼容旧命令，协作人固定为 XenoAmess；不接受其他值。

脚本比较所有文件的 SHA-256，覆盖新增、删除、修改文件。二进制变化仅能确认字节改变。
扫描失败时停止；文本解码失败仍保留字节比较结果和原因，但不假装完成了文本分析。
忽略 .idea、.git、.vscode、.ruff_cache、__pycache__ 和符号链接。

输出 JSON/CSV 和带版本前缀的初步报告，JSON 在文本分析完成后统一导出。
数据字段、统计口径和恢复方式见 [references/evidence.md](references/evidence.md)。

## 当前 Agent 继续解读

脚本完成后，由当前 Agent 继续，不要求用户另行人工触发模型。

1. 先读 JSON 的 summary、version_info、coverage、issues、systems；按需检索 file_diffs 和 deep_diffs，避免整份加载大型 JSON。
2. 将目录分类和机制/AI 关键词视为审查候选。小改动、未分类项、新增与删除文件也要检查；关键机制的一行变化不能因规模小而排除。
3. 对每个要写入结论的关键变更，核实旧版和新版源代码、完整差异块、作用域、触发条件，以及相关定义/调用方。初步报告中被截断的片段不能代替完整证据。
4. 区分“代码事实”“影响推断”“待运行验证”。给事实附相对源码路径、旧/新行号或脚本标识；推测开发目的时明确说是推测，不把关键词当作 Bug 修复证据。
5. 历史日期下的数据初始化不能直接推成所有时间和局面下永久生效的规则。本地化和 UI 变化也不能仅靠路径断言没有玩法影响。
6. 只有在机制和数值含义足够明确时才给 buff/nerf 和策略建议。无法从源代码确定的二进制变化、运行时行为或外部依赖，说明尚未验证。
7. 分批处理大量变更，维护实际复核路径清单。没有复核的范围应明确披露，不能把有限抽查描述为全量解读。

## 最终交付和验收

撰写时读取 [references/reporting.md](references/reporting.md)，其中包含精简模板和可执行验收命令。
最终文件名使用 JSON artifacts.final 和 artifacts.final_bilibili。

- 两份最终报告正文都不得包含 Markdown 表格；代码块中的竖线属于代码，必须保留。
- B 站版是单一独立交付物：所需统计、证据与说明全部内嵌，不能引用 JSON、CSV、初步报告或另一份最终报告来补足内容。允许给出游戏源码路径和报告内部章节引用。
- 开头包含两版游戏/引擎分支及提交和整体统计；未知元信息如实标明，不能编造。
- 末尾“附录 B: 生成信息”用粗体标签列表至少包含报告生成时间、实际分析模型、固定协作人 XenoAmess、脚本深度分析文件数；另列 LLM复核文件数，避免混淆两种覆盖。
- 完成解读后，更新 JSON metadata.analysis_model、metadata.final_generated_at 和 metadata.llm_review：performed=true，reviewed_paths 只填实际核实过的候选文本文件路径。时间使用含时区的 ISO 8601；无法获取完整模型版本时明确注明不可用。
- 执行 validate_report.py，修复统计、覆盖和格式问题后再交付。它不能证明玩法解释正确，仍须核实证据与结论。

报告没有字节数或篇幅指标。以重要变更的可追溯性、覆盖范围的诚实说明和两份交付物的完整性作为完成标准。
